## 一、介绍

### 1.1 痛点：缺陷被记录，但从未被报告

一份邮件文件（`.eml`）出问题时，工程现场的动作是固定的：把文件丢进某个库解出来 → 看不出来不对 → 猜是编码问题 → 换一个库再解一次 → 得到另一种结果。中间缺的那一步是**判定**：这段字节到底违反了哪一条 RFC、在第几个字节、有多严重、是硬规则还是实现差异。

三条实证把这个缺口钉住：

1. **Python 标准库知道有缺陷，但不告诉调用方。** `email.errors` 里定义了 `NoBoundaryInMultipartDefect`、`StartBoundaryNotFoundDefect`、`CloseBoundaryNotFoundDefect`、`MultipartInvariantViolationDefect`、`InvalidBase64PaddingDefect`、`InvalidBase64CharactersDefect`、`InvalidBase64LengthDefect` 等缺陷类。官方文档原句：**"the defects are added to the message where the problem was found"**（✅ 官方文档）。缺陷被**挂到对象上**，不打印、不计数、不打分、不退出非零——调用方不主动遍历 `msg.defects` 就永远不知道。**只记录，不报告。**
2. **标准库的缺陷类里没有 CTE 交叉校验。** 官方 `email.errors` 页列出的缺陷类覆盖边界、base64、头部结构，**没有一类**是"声明的 `Content-Transfer-Encoding` 与正文实际编码不符"（✅ 官方文档逐条核对）。这一层是空的。
3. **标准库仍会漏掉内层 boundary 重复。** cpython #69914（**open**，6 评论）：*"email parser ignores inner multipart boundary when outer message duplicates it"*（✅ issue 原文）。这不是"某个库的小 bug"，而是**宽松解析**的必然结果：当内外层用同一个 boundary，哪个 close-delimiter 属于哪一层在字节层就是有歧义的；宽松解析选一个答案继续走，于是"错"变成了"看起来对"。

于是现场的解法只剩人工：`grep` boundary、数行宽、肉眼找 `=3D`、把附件另存出来看扩展名。这正是本题要替代的动作。

### 统一输出：缺陷记录 + 结构指纹（全模块共用）

每条缺陷是**六元组**，缺一不可：

```json
{
  "rule_id": "MC-B01",
  "class": "hard",              // hard | diff | gray
  "severity": "major",          // blocker | major | minor | note
  "path": "1.2",                // 树路径（见 data/README §7.3）；容器层为 "msg#3"
  "offset": 1248,               // 字节偏移；offset_kind 说明基准
  "offset_kind": "absolute",    // absolute | message-relative | line
  "rfc": "RFC 2046 §5.1.1",     // 出处（无条款支撑时必须显式写 none-by-design）
  "detail": "boundary missing on multipart/* at part 1.2"
}
```

- **`class` 三值封闭**：`hard`（有逐字原句支撑的硬规则）/ `diff`（RFC 无条款或实现分歧，**必须显式标注而非硬判**）/ `gray`（策略项，RFC 未规定）。**没有第四种。**
- **`rfc` 不得为空**：`hard` 必须给到"RFC 号 + 节号"；`diff`/`gray` 必须写 `none-by-design` 或 `RFC 2045 §6.8（仅定义字母表，未定义交叉校验）`——**用"没有条款"本身作为证据，而不是编一个条款**。
- **结构指纹**：`fingerprint = sha256(按 (rule_id, path, offset, class) 排序后的规范 JSON 行)`；另出 `tree_digest = sha256(按 path 排序的 (path, content_type, boundary, body_sha256) 行)`。指纹用于回归比对与跨版本 diff，不是安全摘要。

### 模块 M1 · 树与边界审计（boundary / multipart tree）

- **输入**：单个 `.eml` 文件（模块 M5 下可为 `.mbox`/Maildir 目录）。
- **输出**：`tree.nodes[]`（每节点 `path` / `content_type` / `boundary` / `body_range` / `body_sha256` / `children`）+ 模块 M1 缺陷集。
- **检查面**：
  1. `multipart/*` 缺 `boundary` 参数（MC-B01）——RFC 2046 §5.1.1 原句："The Content-Type field for multipart entities requires one parameter, 'boundary'."
  2. `boundary` 超过 70 字符（MC-B02）——RFC 2046 §5.1.1 原句："must be no longer than 70 characters, not counting the two leading hyphens."
  3. delimiter 未出现在行首（MC-B03）、close-delimiter 形态错误（MC-B04，`--boundary--` 后只允许可忽略的空白与行尾）。**delimiter 形态的 R7 子项本轮未逐字摘录原句 ⇒ 补齐前只出 `note`**（见 `data/README` §三 R7 与 §7.1 未录清单）。
  4. **缺 final boundary**（MC-B05）——`diff` 类：RFC 只描述"truncated entity"，**无恢复规程**；Python 记 `CloseBoundaryNotFoundDefect` 并继续解析。**不硬判**，只登记"树在何处被迫闭合"。
  5. **嵌套复用同一 boundary**（MC-B06）——`hard`：RFC 2046 §5.1.1/§5.1.2 原句："each nested 'multipart' entity uses a different boundary delimiter." 但同时必须输出**歧义说明**：字节层无法唯一确定 close-delimiter 归属，故模块 M1 还须给出"两种候选树"（哪一层先闭合）供人工复核——这正是 cpython #69914 的形状。
  6. preamble / epilogue 存在（MC-B07/MC-B08）——`note`：RFC 2046 §5.1.1 要求**忽略**（该子项原句本轮未逐字摘录，但本条本来就只出 `note`，故不受门禁影响），"存在"本身不是违规，只登记字节区间，用于解释下游"多出来的内容去哪了"。
  7. multipart 无任何 body part（MC-B10）——`hard`，RFC 2045 §6.1 / RFC 2046 §5.1.1：`MultipartInvariantViolationDefect` 的存在即证明"multipart 必须有子部件"是不变量；**本轮未逐字摘录对应原句，故 M1 落地时须先补摘录，未补前该规则只能出 `note`**。
  8. **嵌套深度**（MC-B09）——`gray`：**RFC 未规定最大嵌套深度**。`--max-depth` 是**策略参数**，默认值定义在 `data/README.md` §7.6；超限只出 `gray/note`，**不影响退出码**，除非显式 `--strict-depth`。
- **确定性纪律**：树路径由**字节扫描顺序**决定（不是靠解析器猜测）；同一文件两次运行 `tree_digest` 逐字节一致；boundary 比较按字节（不做大小写折叠）；不把 preamble/epilogue 计入 `body_sha256`。
- **验收**：
  - **复现 cpython #69914**：构造内外层同 boundary 的样本，本工具必须 (a) 报 MC-B06 `hard/major`，(b) 输出两种候选树，(c) 与 `stdlib_compare` 对照显示"标准库未报缺陷"。
  - **手工构造"缺 final boundary"**：本工具必须报 MC-B05 `diff/note` 并标注"树在第 N 字节被迫闭合"，且**退出码不受影响**（证明没把它硬判成错误）。
  - 负例：一个结构完好的 `multipart/mixed` + `multipart/alternative` 嵌套，缺陷数 = 0。

### 模块 M2 · 头编码审计（RFC 2047 / RFC 2231）

- **输入**：模块 M1 产出的每个节点的头块（原始字节，未解码）。
- **输出**：头级缺陷集 + `headers[]`（`name` / `raw_value_sha256` / `octets` / `encoded_words[]` / `params[]`）。
- **检查面**：
  1. encoded-word 长度 > 75（MC-H01）——RFC 2047 §2 原句："An 'encoded-word' may not be more than 75 characters long, including 'charset','encoding','encoded-text', and delimiters."
  2. 含 encoded-word 的头行 > 76 字符（MC-H02）——RFC 2047 §2 原句："each line of a header field that contains one or more 'encoded-word's is limited to 76 characters."
  3. encoded-word 内部出现空白（MC-H03）——`hard`，RFC 2047 §2（"encoded-word" 形态定义，原句见 `data/README` R1/R2 所在节）。**注意**：§6.2 的"相邻 encoded-word 之间 LWSP 显示时忽略"这一子项本轮**未逐字摘录原句**，故该子项在补齐前只出 `note`（见 `data/README` §7.1 未录清单）；MC-H03 本身仍可 `hard`，依据是 §2 而非 §6.2。
  4. Q 编码语法（MC-H04）——`=HH` 必须合法；空格可写 `_`；字面量排除 `= ? _`（RFC 2047 §4.1/§4.2）。**本轮仅核到节号，未逐字摘录原句 ⇒ 补齐前只出 `note`**（见 `data/README` §7.1 未录清单）。
  5. B 编码语法（MC-H05）——即 RFC 2045 base64，**长度必须是 4 的倍数**（RFC 2047 §4.2）。**该子项本轮未逐字摘录原句 ⇒ 补齐前只出 `note`**；§5 的"不得跨 encoded-word 续写"另立 MC-H06（原句已录，可 `hard`）。
  6. encoded-text 跨 encoded-word 续写（MC-H06）——RFC 2047 §5 原句："'encoded-text' MUST NOT be continued from one 'encoded-word' to another."
  7. 头行 > 998 字符（MC-H07）——RFC 5322 §2.1.1 原句："Each line of characters MUST be no more than 998 characters, and SHOULD be no more than 78 characters, excluding the CRLF."
  8. RFC 2231 参数续行（MC-H09）——`name*0` / `name*1` **不得前导零、不得跳号**（RFC 2231 §3）；`charset'language'value` 中**单引号必须存在**（MC-H10，§4）；`%HH` 转义必须合法（MC-H11，§4.1）。**⚠️ R10 整行原句本轮未录 ⇒ MC-H09/H10/H11 在补齐摘录前一律只出 `note`，不得出 `hard`**（见 `data/README` §三 R10 与 §7.1 未录清单）。
  9. 头里出现未编码的非 ASCII 字节（MC-H08）——`diff`：RFC 2047 提供的是编码机制，现实实现常直传 8bit；**不硬判**，只登记偏移与所在头名。
  10. **encoded-word 内部含折行**（MC-H12）——`diff`：折叠发生在解码**之前还是之后**，RFC 未定（SO 52442469 的实样 `=?UTF-8?Q?=C3=A5 =C3=A4?=`）。与 MC-H03 的分工见 `data/README.md` §7.5（判定顺序唯一定义，避免同一字节双记）。
- **确定性纪律**：encoded-word 的字符长度一律按**字节**计（RFC 用的是 characters，而 charset 决定字节→字符映射；本题对 `hard` 判定采用**保守**口径：按编码后的 ASCII 字节数计，因为 encoded-word 本身必须是 ASCII）；不猜测 charset；不把"解码失败"当"缺陷"——解码失败单独记 `decode_error` 而不伪装成某条规则。
- **验收**：
  - **复现 SO 44154520**：`filename*="UTF-8''%D7%A2..."`（**缺 `*0` 序号**）→ 必须报 MC-H09，并给出"按 RFC 2231 §3 应为 `filename*0*=`"的修正提示（提示是文本，不自动改文件）。**严重度在补齐 §3 原句前为 `note`；补齐后提为 `major`。** 该 case 的验收不依赖严重度：只断言"报了 MC-H09 且路径/偏移精确"。
  - **复现 SO 52442469**：encoded-word 内嵌换行 → 必须报 MC-H12 `diff/note`（不是 `hard`），且同一段字节**不得同时**报 MC-H03。
  - 负例：一段合法折叠的多 encoded-word 头（每个 ≤75、行 ≤76、encoded-word 间用 LWSP 分隔）→ 缺陷数 = 0。

### 模块 M3 · 传输编码审计（CTE）

- **输入**：模块 M1 产出的每个叶节点正文（原始字节）+ 该节点的 `Content-Transfer-Encoding` 声明值。
- **输出**：正文级缺陷集 + `body_facts`（`declared_cte` / `observed_shape` / `line_max_octets` / `soft_breaks` / `foreign_chars` / `decoded_sha256`）。
- **检查面**：
  1. **声明与实际不符**（MC-T01）——`diff`，**这是本题最需要克制的一格**：RFC 2045 只在 §2.7/§2.8/§6.1 定义各 CTE 的语义，**没有任何"交叉校验"条款**。因此本规则**永远不出 `hard`**，`rfc` 字段写 `none-by-design`，并在报告里写明"语义层判定，不是条款判定"。
  2. base64 填充非法（MC-T02）、长度非 4 倍数（MC-T03）——RFC 2045 §6.8。**填充细则与"长度须为 4 的倍数"本轮未逐字摘录原句 ⇒ 两条在补齐前只出 `note`**（见 `data/README` §7.1 未录清单）；补齐后可提为 `hard`。
  3. base64 出现字母表外字符（MC-T04）——`note`：RFC 2045 §6.8 原句："Any characters outside of the base64 alphabet are to be ignored in base64-encoded data." → **"忽略"是 RFC 的要求**，所以"出现字母表外字符"本身**不是违规**，只登记（这格正是宽松实现的来源，登记它才能解释下游差异）。
  4. QP 行 > 76（MC-T05）——RFC 2045 §6.7 原句："encoded lines be no more than 76 characters long."
  5. QP 软换行的误用/破坏（MC-T06）——RFC 2045 §6.7 原句："An equal sign as the last character on an encoded line indicates such a non-significant ('soft') line break."
  6. QP 非法转义（MC-T07）——`=` 后不是两位十六进制（SO 79133579 的 `=ustomers` / `=o:p>` / `=ure`）。
  7. QP 二次编码残留（MC-T11）——`diff`：解码后正文里出现字面 `=3D`/`=HH`，说明上游被编码了两次；只登记，不猜责任方。
  8. 未知 CTE 取值（MC-T08）——`diff`，RFC 2045 §6.1（CTE 定义处，本轮未逐字摘录）。
  9. 7bit/8bit 行 > 998 octets（MC-T09）——RFC 2045 §2.7/§2.8。**R11 整行原句本轮未录 ⇒ 补齐前只出 `note`**（见 `data/README` §三 R11）。注：行宽 >998 另可由 MC-H07 依据 RFC 5322 §2.1.1 的**已录原句**判定，但那只覆盖头行，不覆盖正文。
  10. **未声明 CTE 但正文含 8bit 字节**（MC-T10）——`class=hard`（`rfc` 指向 R11 的 §6.1），**但 R11 原句本轮未录 ⇒ 补齐前只出 `note`**（见 `data/README` §三 R11 与 §7.1 未录清单）。
- **确定性纪律**：行宽一律按 **octets**（不含 CRLF/LF）；软换行统计按字节判断（行末 `=` 紧邻线性空白视为 `diff` 而非 `hard`）；base64 解码使用自写解码器，遇到字母表外字符**按 RFC 忽略**并在 `foreign_chars` 计数；不解码即算摘要时明确标注 `decoded_sha256` 的来源。
- **验收**：
  - **复现 SO 79133579（QP 伪影）**：正文含 `=ustomers` → 必须报 MC-T07 `hard/major` 且精确到字节偏移。
  - **复现 SO 6029218（base64 损坏）**：构造长度非 4 倍数的 base64 附件 → 必须报 MC-T03（补齐 §6.8 原句前 `note`，之后 `major`）；另构造"CTE 声明 base64 但正文是明文" → 必须报 MC-T01 `diff/note` 且**退出码不变**（证明没有硬判语义层）。验收断言看 `rule_id` 与偏移，不看严重度。
  - 负例：合法 base64 附件（76 列折行 + 正确填充）→ 缺陷数 = 0；合法 QP 正文（含真实软换行）→ 缺陷数 = 0。

### 模块 M4 · 归属与引用审计（结构层语义，全部 `diff`）

> **本条是纪律，不是漏洞**：`Content-Disposition` 与 `multipart/related` 的规范定义不在本题核对的五部 RFC（2045/2046/2047/2231/5322）之内。按"不得编造条款"的红线，**模块 M4 全部规则一律 `diff` 或 `gray`，不得标 `hard`**。这样做的代价是"不能拿条款压人"，收益是"报告里每一条 `hard` 都经得起查条款"。

- **输入**：模块 M1 的树 + 各节点的 `Content-Type` / `Content-Disposition` / `Content-ID` / 参数集。
- **输出**：归属类缺陷 + `attachments[]`（`path` / `disposition` / `filename` / `name` / `content_id` / `referenced_by[]`）。
- **检查面**：正文与附件归属（MC-A01，SO 6255202「文本附件被当正文」）；`name` 与 `filename` 不一致（MC-A02）；`filename` 缺失（MC-A03，SO 12816042「Noname」）；`cid:` 引用不闭合（MC-A04，SO 10107788）；`multipart/related` 的 `start`/`type` 与实际首部件不一致（MC-A05，SO 39328935「内嵌图不显示」）；`message/rfc822` 转发体的归属与嵌套头（MC-A06）；`inline` 却无 `Content-ID`（MC-A07）；多个叶节点都无可判定 disposition（MC-A08，SO 24246391「正文进了附件」）。
- **确定性纪律**：`filename` 取值必须**先解 RFC 2231 再解 RFC 2047**（顺序写死在 `data/README.md` §7.5，不可两位开发者各写一套）；多个同名参数取**首个**并登记 `duplicate_param`（不静默覆盖）；`cid` 比较按尖括号内字面值、不 URL 解码。
- **验收**：**复现 SO 6255202**（`text/plain` 附件被下游当正文）→ 报 MC-A01 并指出"哪个叶节点缺可判定 disposition"；**复现 SO 12816042**（缺 `filename`）→ 报 MC-A03 并说明下游"Noname"的来源；负例：`multipart/mixed`（正文 + 2 附件）归属全对 → 0 缺陷。

### 模块 M5 ·（可选）容器层审计（mbox / Maildir）

- **输入**：`.mbox` 文件或 Maildir 目录。
- **输出**：消息切分表 + 容器层缺陷。
- **检查面**：`From ` 分隔行无法解析（MC-C01）；`>From` **未转义**导致正文行被误当分隔行（MC-C02）；零长度消息（MC-C03）；正文含 `From ` 行（MC-C04）；Maildir 文件名不合规（MC-C05）。
- **变体纪律（必须写进报告，不是脚注）**：`>From` 转义是 **mboxo 约定，不是 RFC**；mboxrd 与 mboxcl 的转义/长度前缀规则**互不相同**。因此模块 M5 **只出 `diff`**，且报告必须写明"按 mboxo 读"还是"按 mboxrd 读"，同一文件在两种读法下的切分结果**必须同时输出**（`--mbox-variant=mboxo|mboxrd|auto`）。
- **确定性纪律**：切分偏移以**消息起点**为基准（`offset_kind: message-relative`），文件级偏移另记；`auto` 判定规则写死在 `data/README.md` §7.7，不靠启发式打分。
- **验收**：**复现 cpython #93376**（畸形 `From ` 行）→ 报 MC-C01 并给出两种变体下的切分表；**`>From` 样例在 mboxo 与 mboxrd 下切分结果不同**时，两份结果都要落盘，且不得只判其中一种"正确"。

### 扩展项（不进首期判定路径）

- **`--explain`**：给某条规则打印"RFC 原句 + 该文件的字节窗口"（只回放已录入的原文，不联机取 RFC）。
- **`--fix-plan`**：输出"最小改动建议清单"（**只给建议，不写回文件**；写回属另一个产品）。
- **SARIF 输出**：便于 CI 消费。留扩展。

**受众**：① 邮件客户端 / Webmail 开发者（渲染异常定位）；② 邮件服务运维（用户投诉"附件打不开"时给出可复核结论）；③ 邮件归档迁移工程（十年老 `.eml`/`.mbox` 批检）；④ QA（把"某客户端才出错"变成可回归的缺陷集）。

**时代性**：2026 年 MIME 解析库仍在两位数月更，cpython 的边界类缺陷 issue 仍 open——说明**解码能力早已饱和、判定能力仍然缺位**；而合规与归档需求（邮件留存、诉讼取证、迁移验收）要的恰恰是"判定 + 出处"，不是"再解一遍"。

**开源空白三行**：① 解码器有一整排千星级实现，**但都不产出缺陷账本**；② 单个编码算法（QP / RFC 2047 / RFC 2231）各有小库，**但都不判合规**；③ **"每缺陷 = 位置 + 严重度 + RFC 出处 + 硬规则/实现差异"这一格，检索不到——位置空着。**

## 六、边界与非目标

**不做（首期红线）**：

1. **不做邮件认证**。认证语义层（发件人身份验证相关头字段、验证算法、验证结果评估）**整块排除**：不读取、不解析、不判定、不产出任何"可信/不可信"结论。这是与本事另一条产品线的切割线（见头部声明），也是本题"只做结构层"的定义。
2. **不做 TNEF / `winmail.dat` 专向**。那是专有格式解码，越出"结构层"的边界：本题判"这个部件声明了什么、编码对不对"，不判"专有格式内部装了什么"。
3. **不做钓鱼 / URL / 内容安全分析**。该位已有 246★ 的实现，且其判定依赖认证语义，与本题目的一刀切冲突。
4. **不做 `.eml` 浏览器 / 查看器 / 渲染器**。渲染是客户端领地；本题的输出是账本，不是视图。
5. **不做"最大嵌套深度"硬判**。RFC 无规定 → 只能作 `--max-depth` 策略，标 `gray`，默认不影响退出码。
6. **不自动修复、不写回输入文件**。工具只读输入、只写 `--out` 指定路径或 stdout。`--fix-plan` 只出建议文本。
7. **不重实现解码器**。不承诺"比 MimeKit 解得更全"；只承诺"解出来的树 + 缺陷账本可复核"。缺 charset 解码能力时如实报 `decode_error`，不猜。

**隐私红线**：纯本地、零网络（含零遥测、零版本检查）；**真实邮件一律不入仓**——`*.eml` 默认被 `.gitignore` 排除，仅 `data/golden/**` 例外，且该目录只允许合成样本（`example.invalid` 域 + 假附件名），提交前由生成器重跑核对逐字节一致；`fixtures/out/` 与本地输出目录不入仓。

**品牌隔离**：本仓库文档不提名本系列任何其他项目；涉及同类时一律用方向级描述（"认证语义层""解码器"），不落具体项目名。

**首期范围限定**：五模块（模块 M1–M5，M5 可选）、五部 RFC（2045/2046/2047/2231/5322）、单文件与单容器输入。IMAP/POP3 取信、`.msg`（Outlook 二进制）、加密/签名部件（S/MIME、PGP）的内部结构均不在首期。
